## 2. プロジェクト概要 {: #overview }

企業ネットワークの内部インフラを対象としたヘルスチェックツールであり、内部インフラの状態把握を核心価値とする。決定論的な根本原因分析(RCA)を差別化要素とし、完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシーという4原則のもとで設計される。ただし差別化要素であるRCA(F-09)は初期リリース安定後の提供とし、v1(10章)はその土台となる検知・相関キーの記録・構造化出力までを完成範囲とする。

## 3. 背景・目的 {: #background-purpose }

### 3.1 背景
既存の有料競合(PRTG, SolarWinds, Kentik, Datadog, Zabbix等)は高機能だが、クラウド運用やベンダーロックインを前提とすることが多い。一方、個人開発・一人保守という体制では、書き込み機能やクラウドサービス運用に伴う責任(インシデント対応、SLA、データ預託)を個人で負うことは大きな負債になる。この制約下でもなお「エンタープライズ品質」と呼べるツールを成立させることが本プロジェクトの出発点である。

### 3.2 目的
- 内部インフラの状態を、外部からのドメイン監視だけでは得られない粒度で把握できるようにする
- 決定論的なルールベースの根本原因分析により、AIに依存せず「即座に根本原因がわかる」という差別化を実現する(RCA本体(F-09)は初期リリース安定後に段階的に提供し、v1ではその土台となる相関キー付きの観測データ記録までを整える)
- 完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシー の原則により、一人開発者が現実的に負えるリスクの範囲内でエンタープライズ向け品質のツールを提供する
- 日本企業のネットワーク/インフラ担当者を最初のターゲット市場とし、日本語ローカライゼーションを最優先事項として扱う

## 4. 対象ユーザー・ステークホルダー {: #stakeholders }

### 4.1 対象ユーザー
日本企業のネットワーク/インフラ担当者。内部インフラの定期ヘルスチェック、障害発生時の一次切り分けを行いたいユーザー。

### 4.2 ステークホルダー
個人開発(オープンソース)プロジェクトのため、開発者自身が唯一のステークホルダーである。ビジネス化は想定していない。

## 5. 用語定義 {: #glossary }

| 用語 | 定義 |
|---|---|
| <span id="term-core-principles"></span>コアアーキテクチャ原則 | 完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシー の4原則。プロジェクトの初期段階で明文化され、以降のすべての機能・仕様を縛る拘束力を持つ |
| <span id="term-full-local"></span>完全ローカル | 保守者が運用するバックエンドを持たず、ユーザー自身のマシン/サーバー上で動作すること |
| <span id="term-no-cloud"></span>クラウドサービス不要 | 保守者がクラウドインフラの認証情報を一切持たないこと。クラウドを読む場合もユーザー自身のアカウント・認証情報のみを用いる |
| <span id="term-byo"></span>私物利用の方式 | 外部依存(クラウドアカウント、AIモデル/API等)はすべてユーザー自身の選択・アカウントとし、コスト・アクセス・精度リスクをアプリ側ではなくユーザー側が負うこと |
| <span id="term-readonly"></span>読み取り専用ポリシー | アプリが観測・報告のみを行い、ユーザーのインフラに変更を実行しないこと。例外は設けず、修復・設定変更の実行は常にユーザー自身の判断と操作に委ねる |
| <span id="term-rca"></span>決定論的RCA(根本原因分析) | AIに依存せず、グラフ/ルールベースで時系列データと関係性データから根本原因を特定する仕組み。既知パターンに一致しない場合の「原因未特定」も設計上の正式な結果状態として扱う |
| <span id="term-workspace"></span>ワークスペース概念 | マルチテナント/RBAC(複数チーム・組織が1つのインスタンスをアクセス制御付きで共有する仕組み)は現時点では実装しない。ただし、後から追加する際に内部データ構造の作り直しが必要にならないよう、「どのスキャン実行記録・結果がどのチーム/組織に属するか」を区別できる境界を、データ設計の段階からあらかじめ持たせておく方針とする。v1では単一ワークスペース固定(実質1テナント)で運用し、ワークスペースを切り替えるUIやアクセス制御機能自体は提供しない |
| <span id="term-correlation-key"></span>相関キー | 対象識別子・タイムスタンプ・ネットワークセグメント等、複数のチェック結果(F-03〜F-06)を横断して関連付けるための共通属性群。個々のチェックが孤立した結果を返すのではなく、同一対象・近接時間帯で発生した複数の事象をRCA(F-09)が関係づけて推論できるようにするためのもの |
| <span id="term-flapping"></span>フラッピング | チェック結果(正常/異常)が短時間のうちに繰り返し切り替わる不安定な状態。単発の失敗を都度「障害」として扱うと、フラッピング発生時に大量の誤検知・状態遷移が生じるため、F-12はこれを抑制する仕組みを持つ |
| <span id="term-redundant-group"></span>冗長グループ | ユーザーが任意で宣言する、同一の役割を担う複数対象(例: 冗長化されたDNSサーバー2台)の集合(F-13)。トポロジー機能による自動検出ではなく、宣言方式であることが前提 |
| <span id="term-degraded"></span>縮退 | 冗長グループ内の一部(片系)のみが障害している状態。冗長グループが宣言されている場合、これを全体障害ではなく縮退として区別して出力する(F-13) |
| <span id="term-missing-data"></span>欠測 | 本ツール自体が停止・クラッシュしていた期間について、観測データが存在しないこと。監視対象側の障害(到達不能等)とは区別し、RCA(F-09)には障害として渡さない(N-19) |

## 6. 機能要件 {: #functional-requirements }

| No. | 機能名 | 概要 | 優先度 |
|---|---|---|---|
| <span id="F-01"></span>F-01 | 日本語ローカライゼーション | UI/エラーメッセージ/ドキュメントの日本語対応。最優先の製品作業項目 | 必須 |
| <span id="F-02"></span>F-02 | 署名付きリリース体制 | 初期段階から署名付きリリースを確立し、後付けにしない | 必須 |
| <span id="F-03"></span>F-03 | ICMP/SNMPポーリング | 基本的な死活監視・SNMPによる状態取得。SNMPはv1とv3をユーザーが選択できる方式とする(v1: レガシーインフラ向け、v3: 非レガシーインフラ向け) | 必須 |
| <span id="F-04"></span>F-04 | DNS検証 | 設定されたホスト名/レコードを設定されたDNSサーバーに対して問い合わせ、タイムアウト付きで検証する。無応答(タイムアウト)/NXDOMAIN/SERVFAIL/解決結果が期待値と不一致、を区別して結果を出す。結果はF-05/F-06と共通の相関キー(対象識別子・タイムスタンプ・ネットワークセグメント等)で記録し、RCA(F-09)が横断的な関係性を推論できるようにする | 必須 |
| <span id="F-05"></span>F-05 | DHCP検証 | DHCPDISCOVERを送信し、タイムアウト以内にDHCPOFFERが返るかを確認する生存確認。リースプール監視(枯渇・使用率追跡)は対象外。結果はF-04/F-06と共通の相関キーで記録する | 推奨 |
| <span id="F-06"></span>F-06 | NTP検証 | 設定されたNTPサーバーに問い合わせてオフセットを測定し、設定可能なドリフト閾値(デフォルト100ms)と比較する。閾値超過と無応答(サーバー到達不能)は別の結果として扱う。結果はF-04/F-05と共通の相関キーで記録する | 必須 |
| <span id="F-07"></span>F-07 | 構造化出力(JSON/Protobuf) | チェック結果を構造化形式で出力する | 必須 |
| <span id="F-08"></span>F-08 | 時系列データ書き込み抽象化 | Micrometer経由で時系列データを書き込み、特定バックエンドに直結させない | 必須 |
| <span id="F-09"></span>F-09 | 決定論的根本原因分析(RCA) | グラフ/ルールベースのRCA。追加専用のカスタムルールで組み込みルールを上書きしない設計。観測データには「ソース間不一致」(例: SNMPではdownだがICMPは到達可能、のようにチェック間で結果が食い違う状態)も所見の一種として追加し、不一致自体をRCAの検討対象に含める。診断結果は次を含む構造化レポートとして出力する:(1)参照した観測データ(該当する各チェックの結果と相関キー)、(2)検討した関係性(どの観測同士を相関キーで結び付けたか)、(3)結論を導いたルール(該当ルールIDと条件)。既知パターンに一致しない場合は「原因未特定」とし、検討した観測・関係性と、除外した既知パターンの一覧を併せて示す | 推奨(初期リリース安定後) |
| <span id="F-10"></span>F-10 | 時系列データ読み出し抽象化 | InfluxQL/PromQL等を直接叩かず、内部クエリ抽象化層経由で読み出す(F-08と対になる読み出し側の抽象化) | 推奨(F-09と同時期) |
| <span id="F-11"></span>F-11 | スキャンスケジューリングモデル | ハイブリッド方式。単一のスケジューリングエンジンが、常駐デーモンモード(設定可能な間隔での継続ポーリング)とone-shotモード(`--once`等のフラグによる単発実行、手動/外部cron起動向け)の両方を提供する。両モードとも同一の時系列ストアに書き込む | 必須 |
| <span id="F-12"></span>F-12 | 状態遷移の確認ロジック | F-04/F-05/F-06の結果は、単発の失敗のみでは状態遷移とせず、M回中N回の失敗で初めて状態遷移(例: 正常→異常)と判定する。N/M、およびフラッピング抑制の閾値は設定可能とし、既定値は暫定とする。レポートには生の試行結果(raw)と確定状態(confirmed)の両方を出力し、判定過程を隠さない(N-15の可視性と連動) | 必須 |
| <span id="F-13"></span>F-13 | 冗長グループの宣言 | ユーザーが任意で冗長グループ(同一役割を担う複数対象の集合)を宣言できる。宣言された冗長グループ内で片系のみが障害している場合、全体障害ではなく「縮退」候補として結果を出力する。additive方式であり、組み込みルール(F-09のRCA等)の結論を上書き・抑制しない | 推奨 |

| <span id="N-18"></span>N-18 | 自己死活監視 | スケジューリングエンジン自身がハートビートを出力し、監視対象側の到達可能性とは別に、ツール自体(スケジューラ)の停滞・ハングを検知できるようにする |
| <span id="N-19"></span>N-19 | 再起動後の再開性 | クラッシュや再起動の後も、スケジュール設定と保持していた状態を失わずに再開できること。ツール停止中の期間は「欠測」として記録し、当該期間のデータ欠落をネットワーク障害としてRCA(F-09)に渡さない |

## 8. スコープ外 {: #out-of-scope }

- モバイルアプリ版・Webブラウザ版としての提供(将来Webダッシュボードは検討対象だが自己ホスト前提)
- 保守者が運用するクラウドサービス・バックエンド(コアアーキテクチャ原則により対象外)
- 修復・設定変更の自動実行(読み取り専用ポリシーにより、本ツールは対象インフラへの変更を一切実行しない。実行の判断と操作は常に人間が行う)
- 分散アーキテクチャ(実需要が確認されるまで着手しない)
- マルチテナント/RBAC(現時点では未実装。データモデルのみワークスペース概念に開いておく)
- ビジネス化・収益化(想定しない)
- SNMP v2c対応(v1・v3のみサポートし、v2cは当面対象外とする。v1・v3が安定した後、将来的な追加を検討する)
- NetFlow/IPFIX/sFlow等の伝統的フローエクスポートプロトコル対応(v1のポーリングベースのチェックとは異なる収集方式が必要なため、将来検討事項として保留する。放棄ではない)
- streaming telemetry(gNMI等のpush型テレメトリ)対応(v1はポーリングベースの収集モデル(F-11)を採用。N-14のingestion-source抽象化を前提に、将来の追加を検討する)
- 設定変更と障害イベントの相関分析(v1では対応しない。将来検討事項とする)
- アプリケーション層の相関分析やエンドユーザー体感品質の計測はAPM/RUM領域に踏み込むものであり、「内部インフラのヘルスチェック」という本ツールの核心価値とは異なる製品カテゴリになる。v1のスコープ外とし、方向性は将来別途検討する
- アラート・通知機能(メール/Webhook/Slack等への能動的な通知)(v1では対応しない。障害検知後に人間へ知らせる経路が別途必要になるため、将来検討事項とする)
- 可視化・ダッシュボードUI(v1はF-07の構造化出力とF-08/F-10の時系列蓄積までを提供し、人間が見るためのグラフ描画・ダッシュボードは対象外とする。外部可視化ツール(Grafana等)との連携は将来検討事項とする)
- 運用ワークフロー(確認・対応中・解決等のインシデント管理機能)(v1では対応しない。診断結果を人間のチームが引き継いで管理する仕組みは対象外とする)
- 人間可読なレポート生成(v1はJSON/Protobufの構造化出力(F-07)までを提供し、非技術者向けのサマリーレポート生成は対象外とする)
- 履歴調査UI(過去データを人間が閲覧・検索するための専用UI)(時系列データ自体はF-08/F-10で蓄積・抽象化されるが、v1ではRCA(F-09)による内部的な読み出しのみで、人間向けの閲覧UIは提供しない)
- ツール自体のHA/フェイルオーバー(単一ノード・完全ローカル前提のため対象外とする。共有状態の管理やリーダー選出を伴う仕組みは一人開発が現実的に負える範囲を超えるため、将来検討事項ともしない)
- 複数観測点による確認(現時点では単一の観測点からのチェックのみを前提とする。将来の分散アーキテクチャ対応と同時に検討事項とする)
- 冗長グループの自動検出(F-13は宣言方式のみを対象とし、トポロジーからの自動検出は行わない。将来のトポロジー機能と同時に検討事項とする)

- AI機能を実装する場合は私物利用の方式とし、アプリの役割はコンテキスト組み立てのみに限定する。コスト・精度・データ取り扱いリスクはユーザーが選択したモデル側に帰属する
- バックアップ・リカバリはユーザー自身の責任とする。完全ローカルと私物利用の方式の原則により、時系列バックエンド(TimescaleDB等)のバックアップ運用はアプリ側では提供せず、ユーザー自身のデータベース運用に委ねる
- スキーマ・アップグレード時の互換性方針は本書時点では未定。将来バージョンでデータスキーマが変更される場合の移行方針は別途検討する
- プロセスの自動再起動(systemdのRestart=設定、Windowsサービス回復機能等)はユーザー環境側の責任とする。N-19が保証するのは「再起動後に状態を失わず再開できること」であり、「クラッシュ後に自動的に再起動させる」こと自体は本ツールの責務外とする

## 10. 成功基準・完了の定義 {: #success-criteria }

v1として「完成」と呼べる状態を、以下の基準で定義する(暫定、実装・検証を通じて見直す前提):

なお、差別化要素であるRCA(F-09)およびN-15はv1完成基準に含まれない(2章・3.2節参照)。v1の完成は「検知・記録・構造化出力」の完成を意味し、RCAによる根本原因の特定機能の提供を意味しない。

- 必須優先度の機能要件(F-01, F-02, F-03, F-04, F-06, F-07, F-08, F-11)が、実際のネットワーク対象に対して動作し、それぞれ定義された結果状態を正しく区別して返すこと(例: F-04は無応答/NXDOMAIN/SERVFAIL/不一致を区別、F-06は閾値超過と到達不能を区別)
- F-07の構造化出力(JSON/Protobuf)がスキーマに対して検証可能であること
- F-11のハイブリッドスケジューリング(常駐デーモンモード・one-shotモード双方)が同一の時系列ストアに書き込み、N-12の初期ベンチマーク目標(数百ホスト規模・設定可能なポーリング間隔)を満たすこと
- N-10のエラーハンドリング要件どおり、対象到達不能時に例外が握りつぶされず構造化された「到達不能」結果として記録されること
- 日本企業のネットワーク/インフラ担当者が、本ツールを用いて内部インフラの検知・診断(何が起きたか、機械可読な構造化結果としてどう検出されたか)を行える状態にあること。ただし、アラート通知・可視化・運用ワークフロー・人間可読レポート・履歴調査UI(8章参照)はv1のスコープ外であり、これらは外部ツールとの組み合わせ、または将来バージョンでの対応を前提とする
- F-04/F-05/F-06の結果が共通の相関キー(対象識別子・タイムスタンプ・ネットワークセグメント等)で記録され、同一対象・近接時間帯に発生した複数チェックの結果を突き合わせられること(相関キーの記録自体は必須優先度のF-04/F-06に含まれるため検証対象とする。ただしF-09のRCA、およびそれに依存するN-15は、v1完成基準には含めない)
- 単発の失敗(1回のみ)では状態遷移(F-12)が発生しないこと
- 冗長グループ(F-13)内の片系障害が「縮退」として判定されること
- ハートビート停止(N-18)が検知されること
- 再起動後の欠測期間(N-19)がネットワーク障害として誤判定されないこと
- N-16のデータ保持・プルーニングポリシーどおり、設定した保持期間を超えた時系列データが自動的にプルーニングされることを確認すること(F-11の常駐デーモンモードが必須優先度であるため、長期稼働時のストレージ肥大化防止は検証対象とする)
