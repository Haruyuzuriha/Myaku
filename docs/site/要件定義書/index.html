2. プロジェクト概要¶

企業ネットワークの内部インフラを対象としたヘルスチェックツールであり、内部インフラの状態把握を核心価値とする。決定論的な根本原因分析(RCA)を差別化要素とし、完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシーという4原則のもとで設計される。

3. 背景・目的¶

3.1 背景¶

既存の有料競合(PRTG, SolarWinds, Kentik, Datadog, Zabbix等)は高機能だが、クラウド運用やベンダーロックインを前提とすることが多い。一方、個人開発・一人保守という体制では、書き込み機能やクラウドサービス運用に伴う責任(インシデント対応、SLA、データ預託)を個人で負うことは大きな負債になる。この制約下でもなお「エンタープライズ品質」と呼べるツールを成立させることが本プロジェクトの出発点である。

3.2 目的¶

  • 内部インフラの状態を、外部からのドメイン監視だけでは得られない粒度で把握できるようにする
  • 決定論的なルールベースの根本原因分析により、AIに依存せず「即座に根本原因がわかる」という差別化を実現する
  • 完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシー の原則により、一人開発者が現実的に負えるリスクの範囲内でエンタープライズ向け品質のツールを提供する
  • 日本企業のネットワーク/インフラ担当者を最初のターゲット市場とし、日本語ローカライゼーションを最優先事項として扱う

4. 対象ユーザー・ステークホルダー¶

4.1 対象ユーザー¶

日本企業のネットワーク/インフラ担当者。内部インフラの定期ヘルスチェック、障害発生時の一次切り分けを行いたいユーザー。

4.2 ステークホルダー¶

個人開発(オープンソース)プロジェクトのため、開発者自身が唯一のステークホルダーである。ビジネス化は想定していない。

5. 用語定義¶

用語 定義
コアアーキテクチャ原則 完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシー の4原則。プロジェクトの初期段階で明文化され、以降のすべての機能・仕様を縛る拘束力を持つ
完全ローカル 保守者が運用するバックエンドを持たず、ユーザー自身のマシン/サーバー上で動作すること
クラウドサービス不要 保守者がクラウドインフラの認証情報を一切持たないこと。クラウドを読む場合もユーザー自身のアカウント・認証情報のみを用いる
私物利用の方式 外部依存(クラウドアカウント、AIモデル/API等)はすべてユーザー自身の選択・アカウントとし、コスト・アクセス・精度リスクをアプリ側ではなくユーザー側が負うこと
読み取り専用ポリシー アプリが観測・報告のみを行い、ユーザーのインフラに変更を実行しないこと(唯一の例外であるリメディエーション機能も推奨のみに限定)
決定論的RCA(根本原因分析) AIに依存せず、グラフ/ルールベースで時系列データと関係性データから根本原因を特定する仕組み。既知パターンに一致しない場合の「原因未特定」も設計上の正式な結果状態として扱う
ワークスペース概念 マルチテナント/RBAC(複数チーム・組織が1つのインスタンスをアクセス制御付きで共有する仕組み)は現時点では実装しない。ただし、後から追加する際に内部データ構造の作り直しが必要にならないよう、「どのスキャン実行記録・結果がどのチーム/組織に属するか」を区別できる境界を、データ設計の段階からあらかじめ持たせておく方針とする。v1では単一ワークスペース固定(実質1テナント)で運用し、ワークスペースを切り替えるUIやアクセス制御機能自体は提供しない
相関キー 対象識別子・タイムスタンプ・ネットワークセグメント等、複数のチェック結果(F-03〜F-06)を横断して関連付けるための共通属性群。個々のチェックが孤立した結果を返すのではなく、同一対象・近接時間帯で発生した複数の事象をRCA(F-09)が関係づけて推論できるようにするためのもの

6. 機能要件¶

No. 機能名 概要 優先度
F-01 日本語ローカライゼーション UI/エラーメッセージ/ドキュメントの日本語対応。最優先の製品作業項目 必須
F-02 署名付きリリース体制 初期段階から署名付きリリースを確立し、後付けにしない 必須
F-03 ICMP/SNMPポーリング 基本的な死活監視・SNMPによる状態取得。SNMPはv1とv3をユーザーが選択できる方式とする(v1: レガシーインフラ向け、v3: 非レガシーインフラ向け) 必須
F-04 DNS検証 設定されたホスト名/レコードを設定されたDNSサーバーに対して問い合わせ、タイムアウト付きで検証する。無応答(タイムアウト)/NXDOMAIN/SERVFAIL/解決結果が期待値と不一致、を区別して結果を出す。結果はF-05/F-06と共通の相関キー(対象識別子・タイムスタンプ・ネットワークセグメント等)で記録し、RCA(F-09)が横断的な関係性を推論できるようにする 必須
F-05 DHCP検証 DHCPDISCOVERを送信し、タイムアウト以内にDHCPOFFERが返るかを確認する生存確認。リースプール監視(枯渇・使用率追跡)は対象外。結果はF-04/F-06と共通の相関キーで記録する 推奨
F-06 NTP検証 設定されたNTPサーバーに問い合わせてオフセットを測定し、設定可能なドリフト閾値(デフォルト100ms)と比較する。閾値超過と無応答(サーバー到達不能)は別の結果として扱う。結果はF-04/F-05と共通の相関キーで記録する 必須
F-07 構造化出力(JSON/Protobuf) チェック結果を構造化形式で出力する 必須
F-08 時系列データ書き込み抽象化 Micrometer経由で時系列データを書き込み、特定バックエンドに直結させない 必須
F-09 決定論的根本原因分析(RCA) グラフ/ルールベースのRCA。追加専用のカスタムルールで組み込みルールを上書きしない設計。診断結果は次を含む構造化レポートとして出力する:(1)参照した観測データ(該当する各チェックの結果と相関キー)、(2)検討した関係性(どの観測同士を相関キーで結び付けたか)、(3)結論を導いたルール(該当ルールIDと条件)。既知パターンに一致しない場合は「原因未特定」とし、検討した観測・関係性と、除外した既知パターンの一覧を併せて示す 推奨(初期リリース安定後)
F-10 時系列データ読み出し抽象化 InfluxQL/PromQL等を直接叩かず、内部クエリ抽象化層経由で読み出す(F-08と対になる読み出し側の抽象化) 推奨(F-09と同時期)
F-11 スキャンスケジューリングモデル ハイブリッド方式。単一のスケジューリングエンジンが、常駐デーモンモード(設定可能な間隔での継続ポーリング)とone-shotモード(--once等のフラグによる単発実行、手動/外部cron起動向け)の両方を提供する。両モードとも同一の時系列ストアに書き込む 必須

7. 非機能要件¶

No. 分類 内容
N-01 プラットフォーム 本書時点では未確定。初期段階はUI形態を特定せず、サーバー/ヘッドレス的な運用を想定。JavaFX UIを前提としない柔軟なデプロイ(ヘッドレス/サーバーモード)は将来的な検討対象とする
N-02 実行環境の原則 コアアーキテクチャ原則に従うこと。クラウドテレメトリ取り込み(将来対応)も、デフォルトでは無効とし、ユーザーが明示的に認証情報を設定した場合のみ有効になること
N-03 実装言語・技術スタック 未定
N-04 開発体制 一人での開発。オープンソースとして公開する
N-05 データベース・時系列ストレージ TimescaleDBを主要(デフォルト)バックエンドとして要求する。特定バックエンドへの直結は避けるpluggable設計とし、マルチバックエンド対応を公に謳う前に、最低2つのバックエンド(TimescaleDB含む)で書き込み・読み出し両方の抽象化層を検証すること。TimescaleDBはユーザー自身の環境での構築が前提となるため、セットアップ手順をドキュメントで明示すること(zero-configではない旨を明記)
N-06 ローカライゼーション 日本語UI/エラーメッセージ/ドキュメントを最優先実装する(N-01と関連)
N-07 保守性・拡張性 「どのスキャン実行記録・結果がどのチーム/組織に属するか」を区別できる境界を、データ設計の段階からあらかじめ持たせ、将来のマルチテナント/RBAC追加に備える。v1では単一ワークスペース固定で運用し、ワークスペース切り替えUI/アクセス制御は実装しない(詳細は5章「workspace概念」参照)
N-08 認証情報・シークレット管理 SNMPコミュニティ文字列・DB接続情報等はOSネイティブのキーチェーン/認証情報ストアへの保存を優先し、対応しない環境では暗号化ローカルファイルにフォールバックする。平文設定ファイルへの保存は行わない
N-09 パッケージング 署名付きJAR形式で配布する(JVM前提)。ネイティブバイナリ化は本書時点では対象外
N-10 エラーハンドリング・ロギング 対象到達不能時は例外を握りつぶさず、構造化された「到達不能」結果として返す。ログはレベル・タイムスタンプ・対象・チェック種別を含む構造化形式とする
N-11 デーモンライフサイクル 常駐デーモンモード(F-11)は正常な起動・停止をサポートし、長期稼働時のログ肥大化を防ぐログローテーションを備えること
N-12 性能・スケール目標 初期目標として数百ホスト規模・設定可能なポーリング間隔・低いアイドル時リソースフットプリントを暫定基準とする。実測ベンチマークにより本書時点の数値は今後見直す
N-13 対応OS Linux・Windowsを公式サポート対象(テスト・バグ報告受付の対象)とする。macOS版もリリースするが、公式テスト対象外とする
N-14 ingestion-source抽象化 チェック実行(F-03〜F-06等)のデータ収集経路を抽象化する。現時点ではポーリング方式(F-11)のみを実装するが、将来streaming telemetry等のpush型収集を追加する際に、既存のスケジューリング/収集の仕組みを作り直さずに拡張できるアーキテクチャとする
N-15 診断プロセスの可視性 RCA(F-09)の結論(または「原因未特定」の判定)に至るまでの過程を、エンジニアが検証可能な形でユーザーに提示すること。具体的には、参照した観測データ・相関キーで結び付けた関係性・適用されたルールを黙って隠さず出力すること。これは本プロジェクトの差別化要素(観測から結論までを追跡できる、決定論的で説明可能な診断)を成立させる上で必須の要件とする
N-16 データ保持・プルーニングポリシー 時系列データの保持期間を設定可能にし、デフォルト保持期間(暫定90日)を超えたデータは自動的にプルーニングする。常駐デーモンモード(F-11/N-11)による無期限蓄積がストレージ肥大化やN-12の性能目標を損なうことを防ぐ
N-17 ローカルアクセス制御の前提 v1はマルチテナント/RBACを実装しないことに伴い、単一の信頼されたローカルユーザーが直接操作することを前提とし、認証機構は設けない。将来、常駐デーモンモード(F-11)がネットワーク越しにアクセス可能なインターフェース(API/Webダッシュボード等)を提供する場合は、その時点で認証機構を追加できる設計上の余地を残す

8. スコープ外¶

  • モバイルアプリ版・Webブラウザ版としての提供(将来Webダッシュボードは検討対象だが自己ホスト前提)
  • 保守者が運用するクラウドサービス・バックエンド(コアアーキテクチャ原則により対象外)
  • リメディエーションの自動実行(読み取り専用ポリシーにより、設定ドリフト検知は推奨のみに限定。人間による実行判断を必須とする)
  • 分散アーキテクチャ(実需要が確認されるまで着手しない)
  • マルチテナント/RBAC(現時点では未実装。データモデルのみワークスペース概念に開いておく)
  • ビジネス化・収益化(想定しない)
  • SNMP v2c対応(v1・v3のみサポートし、v2cは当面対象外とする。v1・v3が安定した後、将来的な追加を検討する)
  • NetFlow/IPFIX/sFlow等の伝統的フローエクスポートプロトコル対応(v1のポーリングベースのチェックとは異なる収集方式が必要なため、将来検討事項として保留する。放棄ではない)
  • streaming telemetry(gNMI等のpush型テレメトリ)対応(v1はポーリングベースの収集モデル(F-11)を採用。N-14のingestion-source抽象化を前提に、将来の追加を検討する)
  • 設定変更と障害イベントの相関分析(M10相当の設定ドリフト検知とは別軸の機能であり、v1では対応しない。将来検討事項とする)
  • アプリケーション層の相関分析やエンドユーザー体感品質の計測はAPM/RUM領域に踏み込むものであり、「内部インフラのヘルスチェック」という本ツールの核心価値とは異なる製品カテゴリになる。v1のスコープ外とし、方向性は将来別途検討する
  • アラート・通知機能(メール/Webhook/Slack等への能動的な通知)(v1では対応しない。障害検知後に人間へ知らせる経路が別途必要になるため、将来検討事項とする)
  • 可視化・ダッシュボードUI(v1はF-07の構造化出力とF-08/F-10の時系列蓄積までを提供し、人間が見るためのグラフ描画・ダッシュボードは対象外とする。外部可視化ツール(Grafana等)との連携は将来検討事項とする)
  • 運用ワークフロー(確認・対応中・解決等のインシデント管理機能)(v1では対応しない。診断結果を人間のチームが引き継いで管理する仕組みは対象外とする)
  • 人間可読なレポート生成(v1はJSON/Protobufの構造化出力(F-07)までを提供し、非技術者向けのサマリーレポート生成は対象外とする)
  • 履歴調査UI(過去データを人間が閲覧・検索するための専用UI)(時系列データ自体はF-08/F-10で蓄積・抽象化されるが、v1ではRCA(F-09)による内部的な読み出しのみで、人間向けの閲覧UIは提供しない)

9. 制約条件・前提条件¶

  • コアアーキテクチャ原則(完全ローカル / クラウドサービス不要 / 私物利用の方式 / 読み取り専用ポリシー)は明文化されており、すべての機能要件・非機能要件はこの原則に照らして検証される
  • 日本企業向け市場を最初のターゲットとし、他市場への展開はその後とする
  • 法務・コンプライアンスは、OSSライセンス選定、依存関係のライセンス監査、不正使用報告窓口、ToS/免責文言、サポート・信頼性コミットメントを早期から並行して進める。公開する前には商標調査・法人化・制裁リスト地理制限確認・専門家による法務レビューを必須ゲートとする
  • 一人開発であることに起因し、サポート・保守体制は現実的に負える範囲に限定する
  • AI機能を実装する場合は私物利用の方式とし、アプリの役割はコンテキスト組み立てのみに限定する。コスト・精度・データ取り扱いリスクはユーザーが選択したモデル側に帰属する
  • バックアップ・リカバリはユーザー自身の責任とする。完全ローカルと私物利用の方式の原則により、時系列バックエンド(TimescaleDB等)のバックアップ運用はアプリ側では提供せず、ユーザー自身のデータベース運用に委ねる
  • スキーマ・アップグレード時の互換性方針は本書時点では未定。将来バージョンでデータスキーマが変更される場合の移行方針は別途検討する

10. 成功基準・完了の定義¶

v1として「完成」と呼べる状態を、以下の基準で定義する(暫定、実装・検証を通じて見直す前提):

  • 必須優先度の機能要件(F-01, F-02, F-03, F-04, F-06, F-07, F-08, F-11)が、実際のネットワーク対象に対して動作し、それぞれ定義された結果状態を正しく区別して返すこと(例: F-04は無応答/NXDOMAIN/SERVFAIL/不一致を区別、F-06は閾値超過と到達不能を区別)
  • F-07の構造化出力(JSON/Protobuf)がスキーマに対して検証可能であること
  • F-11のハイブリッドスケジューリング(常駐デーモンモード・one-shotモード双方)が同一の時系列ストアに書き込み、N-12の初期ベンチマーク目標(数百ホスト規模・設定可能なポーリング間隔)を満たすこと
  • N-10のエラーハンドリング要件どおり、対象到達不能時に例外が握りつぶされず構造化された「到達不能」結果として記録されること
  • 日本企業のネットワーク/インフラ担当者が、本ツールを用いて内部インフラの検知・診断(何が起きたか、機械可読な構造化結果としてどう検出されたか)を行える状態にあること。ただし、アラート通知・可視化・運用ワークフロー・人間可読レポート・履歴調査UI(8章参照)はv1のスコープ外であり、これらは外部ツールとの組み合わせ、または将来バージョンでの対応を前提とする
  • F-04/F-05/F-06の結果が共通の相関キー(対象識別子・タイムスタンプ・ネットワークセグメント等)で記録され、同一対象・近接時間帯に発生した複数チェックの結果を突き合わせられること(相関キーの記録自体は必須優先度のF-04/F-06に含まれるため検証対象とする。ただしF-09のRCA、およびそれに依存するN-15は、v1完成基準には含めない)
  • N-16のデータ保持・プルーニングポリシーどおり、設定した保持期間を超えた時系列データが自動的にプルーニングされることを確認すること(F-11の常駐デーモンモードが必須優先度であるため、長期稼働時のストレージ肥大化防止は検証対象とする)
